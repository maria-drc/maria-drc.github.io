## The one rule that matters most

**Projects live only in `projects/*.qmd`. Every view of a project —
the homepage board, the finished-projects list, the project's own
page — reads from that file. Never hand-write a project's title,
description, or write-up into a second place.**

The homepage does NOT hand-code project content. `index.qmd` contains
only the bio block and one line, `{{< include _generated/board.qmd >}}`.
`_generated/board.qmd` is a **build artifact**, regenerated by
`scripts/build_board.py` on every `quarto render`/`quarto preview` (wired
in as a `project.pre-render` step in `_quarto.yml`). Never hand-edit
`_generated/board.qmd` — it will be overwritten.

Important quirk: `_generated/board.qmd` **is committed to git**, not
gitignored, even though it's generated. Quarto's project scanner
resolves `{{< include >}}` targets *before* running pre-render scripts,
so on a fresh clone the include fails if the file doesn't already exist
on disk. Pre-render then refreshes its contents on every subsequent
render. If you ever see "Include directive failed" on a clean checkout,
run `python3 scripts/build_board.py` once by hand, then render normally.

## Frontmatter schema (`projects/_template.qmd`)

```yaml
---
title: "..."
category: llm-agent-behaviour     # exactly one slug from taxonomy.yml
labels: [AI Agents, Benchmarks]   # one or more, all must exist in taxonomy.yml
image: images/....jpg             # optional — full-resolution, used on the project's own page; omit entirely for a no-image card (a review/working paper with nothing to show), and also omit thumbnail below
thumbnail: images/thumbs/....jpg  # 600px wide, used on homepage cards — see below
date: YYYY-MM
paper: https://...
venue: "arXiv"                    # or journal name
description: "One sentence, plain language, for the grid card."
order: 1                          # optional, ascending, sorts within its category on the homepage board — omit for the default (alphabetical by filename, same as no field at all)
---

Longer write-up as the body — the full paragraphs, the full-res figure(s),
a "Read more"/paper link. This is the ONLY place this text lives.
```

`scripts/build_board.py` sorts each category's cards by `order` (a project
without one sorts after any that have it, at a large default value, so
"no particular order needed" categories are unaffected) — use it sparingly,
only when a project genuinely needs to jump the queue (e.g. a new paper
that should lead its column), since most projects should never need it.

## labels vs. category — do not conflate these

Two independent axes, both defined in `taxonomy.yml`:

- **`labels`** — many per project, fine-grained topic tags, used for
  display (pills on cards) and eventually filtering. This is the
  **stable, long-lived** layer. **Append-only in spirit**: when in doubt,
  add a new label rather than rename an existing one — renaming silently
  changes the meaning of every project already using it, and there's no
  validation to catch that (validation only checks the label exists, not
  that its meaning hasn't drifted).
- **`category`** — exactly one per project, controls *only* which
  homepage section it appears in and the section order. This is the
  **volatile** layer — expected to be renamed/merged/reordered over
  time. Keys (slugs) are stable identifiers; only the slug is written
  into project frontmatter, so renaming a category's display name is a
  one-line edit in `taxonomy.yml` that every project picks up
  automatically.

Note: the label set was deliberately consolidated once, from ~19 narrow
labels down to 9 broad ones (`taxonomy.yml` is the source of truth for
the current list — check it, don't assume from memory). That was a
one-time, explicitly-requested exception to "append-only" — every
project's `labels:` got rewritten to fit the new set, and several niche
labels (misinformation, digital public goods, skill mismatch, etc.) were
retired with no replacement, so some projects now carry just one tag.
Going forward, treat the *current* set as the stable layer again —
append-only-in-spirit still applies from here on; don't casually add
narrow one-off labels back, the whole point was fewer, broader tags that
work well as filter buttons.

Never infer one from the other. A project's labels don't imply its
category and vice versa — assign both explicitly.

## Taxonomy operations

All of these are edits to `taxonomy.yml` only, never to individual
project files, except merges (below):

- **Add a label**: append it to the `labels:` list in `taxonomy.yml`.
  Then reference it in whichever projects need it.
- **Rename a category**: change its `name:` value. The `slug:` (the key
  every project references) stays the same, so no project files change.
- **Reorder categories**: reorder the `categories:` list. Homepage
  section order, and mobile reading order (columns collapse to one
  column and stack in this same order) both follow automatically.
- **Add a category**: append a new `{slug, name}` entry at the position
  you want it to appear. A category with zero projects referencing it
  simply doesn't render a column (see `build_board.py`) — you can add
  the taxonomy entry before or after creating its first project.
- **Merge two categories**: pick which slug survives, delete the other
  entry from `taxonomy.yml`, then find-replace the old slug with the
  surviving one across `projects/*.qmd` frontmatter, e.g.:
  `grep -rl 'category: old-slug' projects/ | xargs sed -i '' 's/category: old-slug/category: new-slug/'`
- **Move a project to Finished projects**: change that one project's
  `category:` field to `finished-projects`. Nothing else to touch — it
  moves from the multi-column board to the full-width simple list on
  the next render.

`scripts/validate_taxonomy.py` runs as a `pre-render` step and fails the
build (non-zero exit) if any project references a `category` or `labels`
entry not present in `taxonomy.yml` — this is what catches typos instead
of silently creating a new, uncontrolled tag. Test it's still working
after editing taxonomy by temporarily typo-ing a category and confirming
`quarto render` fails, the way it was verified during the build.

## Homepage board (`scripts/build_board.py`)

Reads `taxonomy.yml` + every `projects/*.qmd` frontmatter and emits
`_generated/board.qmd`: one column per non-finished category (in
`taxonomy.yml` order, CSS `repeat(auto-fit, minmax(240px, 1fr))` so the
count is derived, never hardcoded), each with that category's projects as
cards, sorted by the optional `order:` field (see Frontmatter schema
above). Below the board, a flat card grid (`.finished-grid`, same card
markup, no sub-category columns) for `finished-projects` under the
heading "Other research" — this section deliberately does NOT split
further by category; "no particular order needed" is the default there.

The script also computes, on every run, which non-finished column has
the fewest projects, and appends a quiet link block (Publications +
Google Scholar) to the foot of *that* column — this is deliberate, not a
placeholder: it fills a short column with something useful instead of
leaving dead space, and it moves on its own if project counts shift, so
nobody has to remember to relocate it by hand. Don't hardcode which
column it goes in.

### Card markup (`card_html()`) — no nested `<a>`s

A card is a `<div class="project-card">` containing **two separate**
`<a class="project-card-link">` elements — one wrapping just the title,
one wrapping just the thumbnail `<img>` — plus a `<p class="project-card-desc">`
that is *not* inside either anchor. The paper link (`Read the paper →`)
lives inside that same `<p>`, right after the description text, so it
reads inline. This split exists because HTML doesn't allow nesting an
`<a>` inside another `<a>` — a single card-wide anchor wrapping
title+desc+thumbnail would make the paper link's own `<a>` invalid and
break click targeting. If you touch this markup, keep the two-anchor
split; don't collapse it back into one wrapping link.

A project with no `image`/`thumbnail` (e.g. a review with nothing to
show) simply omits the thumbnail `<a>` entirely — `card_html()` checks
`if thumb` before emitting it. Don't add a placeholder/broken-image
fallback; no image is a valid, supported state.

### Tag filtering (`js/board-filter.js`, `filter_bar_html()`)

The filter bar (multi-select, match-any) and each card's `data-labels`
attribute are generated by `build_board.py`; `js/board-filter.js` (a
plain script tag in `index.qmd`, not wired through `_quarto.yml`) does
the actual show/hide. Two non-obvious things if you ever touch this:

- **Never `display:none` a whole `.board-column` or a `.project-card`
  itself** when it has no matches. Both are direct CSS grid items
  (`.board-column` inside `.project-board`; `.project-card` inside
  `.finished-grid`), and `auto-fit` collapses the track of any grid item
  actually removed from flow, stretching the remaining ones to fill the
  row — which is exactly the "cards balloon to full width when filtered"
  bug hit twice during this build. Instead: hide a card's *children*
  (`.project-card.is-hidden > * { display: none }`) so the outer div
  stays a real, present, ~0-height grid item — its column track is
  preserved but empty. `.board-column`'s cards/title all individually
  collapse this way too, so the column itself never needs hiding at all.
- Filtering also toggles `body.is-filtered`, which hides
  `.board-column-title`/`.finished-title` (filtered results should read
  as a flat set of matches, not still grouped under a category label)
  and strips `.finished-section`'s border-top (otherwise a lone filtered
  match sits under a floating, now-unlabelled divider rule).

`index.qmd`'s board section is wrapped in `::: {.column-screen} :::` so
it can render up to `max-width: 1400px` (see `styles.scss`) even though
`_quarto.yml`'s `grid.body-width: 900px` keeps ordinary prose pages (and
the homepage's own bio block, which is deliberately left *outside* that
wrapper) at a normal reading width. If you ever need the board wider or
narrower, change `.project-board`'s `max-width` in `styles.scss` — leave
`grid.body-width` alone, it's correct for prose.

## Images

- Location: `images/` at repo root, referenced from `.qmd` files as
  root-relative paths (`/images/....jpg`) — this works because the site
  deploys at a domain root (`rmariadelriochanona.github.io`); it would
  need reconsidering if the site ever moved to a project-repo subpath.
- Filenames: descriptive, not source slugs (`us-decarbonisation-employment.jpg`,
  not `fx1_lrg.jpg`).
- Target ~1200px wide, compressed, for full-resolution project images.
  (Note: the 11 images migrated in Phase 1 are at their original
  archive resolution, not resampled to this target — treat 1200px as
  the standard for anything new, not a retroactive requirement.)
- Alt text is required: `fig-alt="..."` on markdown `![]()` images in
  project bodies; the board generator auto-derives `alt` from the
  project title for cards.

### Thumbnails (`images/thumbs/`, `scripts/generate_thumbnails.py`)

Card thumbnails are **not** produced by blindly downscaling the
full-resolution figure — dense multi-panel plots turn into unreadable
soup at 600px wide. This is a curatorial step:

1. Look at the source image yourself before deciding.
2. If it's a single clean panel/diagram, a straight downscale is fine —
   add `"filename.png": None` to the `CROPS` dict in
   `scripts/generate_thumbnails.py`.
3. If it's multi-panel, a dense table, or has small text, pick a crop
   box (in original-image pixel coordinates) that isolates the single
   most legible/representative region — add
   `"filename.png": (left, top, right, bottom)`.
4. Run `python3 scripts/generate_thumbnails.py`, then actually look at
   the output in `images/thumbs/` before moving on (re-crop if a header
   or axis label got clipped).
5. Add a `thumbnail: images/thumbs/....jpg` field to the project's
   frontmatter alongside its full-resolution `image:` field.

Gotcha already hit once: source PNGs with an alpha channel will render
with a **black** background if you `.convert("RGB")` directly — you have
to composite onto white first. `generate_thumbnails.py`'s `make_thumb()`
already handles this; keep that logic if you ever rewrite it.

Do **not** apply `object-fit: cover` with a fixed `aspect-ratio` to
`.project-card-thumb` in CSS — that re-crops thumbnails a second time on
top of the deliberate crop above, which is how a previous version of
this ended up chopping headers off. Thumbnails render at their natural
aspect ratio (`width: 100%; height: auto;`). This applies everywhere
`.project-card-thumb` is used — both the main board and the "Other
research" grid render the exact same card markup (see Homepage board
above), so there's only one thumbnail rule to keep correct.

## Blog

- Posts: `blog/posts/YYYY-MM-DD-slug.qmd`, frontmatter `title`, `date`,
  `image` (optional). `blog/index.qmd` is a Quarto `listing` over
  `posts/`, sorted `date desc` — adding a post file is the only step,
  no index edits needed.
- **Known gap**: the brief asked for the "Blog" navbar item to
  auto-hide when there are zero posts. This is not implemented —
  `_quarto.yml`'s navbar is static YAML and doesn't currently have
  conditional logic. If this needs doing: a pre-render script can't
  rewrite `_quarto.yml` itself (chicken-and-egg — Quarto reads
  `_quarto.yml` to learn what pre-render scripts to run, before they've
  run), so the workable approach is likely a small manual step
  (comment out the navbar entry if `blog/posts/` is ever emptied) or a
  wrapper script outside Quarto's own render lifecycle. Flag this to
  Maria if it becomes relevant rather than guessing at a fix.

## Adding things

- **New project**: copy `projects/_template.qmd`, fill in frontmatter
  (`category` and every `labels` entry must already exist in
  `taxonomy.yml` — the pre-render check will catch typos), write the
  body, add the full-res image to `images/`, generate its thumbnail (see
  above), run `quarto preview` and confirm it shows up in the right
  board column and that its tags filter correctly (cards no longer show
  label pills themselves — `data-labels` is used only by the filter bar).
- **New talk**: add a bullet to the relevant list in
  `podcasts-talks.qmd` (hand-maintained, no generation) — keep the
  existing reverse-chronological ordering within "Upcoming and previous
  talks."
- **New paper for Publications**: once Phase 4 exists, re-export the
  `.bib` from the Google Scholar profile (`user=HwK5iiEAAAAJ`) and re-run
  its generator script (not yet written — will live at
  `scripts/bib_to_qmd.py` per the original plan) to regenerate
  `publications.qmd`. Don't hand-edit `publications.qmd`.

## Before any commit

Run `quarto preview` and actually look at the page you changed — the
taxonomy validator and board generator both run automatically as
pre-render steps, so a broken category/label reference or a malformed
project file will fail the render rather than silently shipping.
